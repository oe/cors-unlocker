# Wireflip 2.1.0 release notes

Rollout began on 2026-10-19. Firefox 2.1.0 is public; Chrome 2.1.0 is submitted for review with automatic publication. SDK 2.1.0 publication is in progress. General availability awaits independent verification of all three channels.

| Channel | Release version | Previously verified public version |
| --- | --- | --- |
| Chrome extension | 2.1.0 | 2.0.0 |
| Firefox extension | 2.1.0 | 2.0.0 |
| npm `wireflip` SDK | 2.1.0 | 0.2.0 |

The SDK jumps directly from 0.2.0 to 2.1.0 to share the extension's product version. Keep these versions aligned for future coordinated releases.

## Website changes stay under your control

Websites must ask for approval in a Wireflip-owned window before enabling or disabling CORS, creating drafts, or creating, updating, enabling, disabling and deleting their rules. Untrusted websites must request the change from a click or keyboard action. Cancelling or closing the window leaves the operation unapplied.

To allow a site to manage the rules it created without repeated prompts, open the extension popup, expand **Website control**, and explicitly enable trust. Trust applies only to the exact site origin, including scheme and port. Requests that grant access to login credentials still require confirmation. Revoking trust restores prompts; it does not disable or delete saved rules. The menu also shows the latest completed website operation.

Websites cannot take control of manually created, older unowned or other-origin rules. Manage those in **Wireflip → Rules**. If you want the website to create a new owned CORS rule, delete its old CORS rule there and retry from the website. Trust does not transfer existing rule ownership.

## Saved rules run automatically

Enabled saved rules run on matching supported pages, including other tabs from the same scoped origin. Recording and temporary tab controls are separate: stopping recording does not stop saved rules. Disable the rule or its group to stop it. Previously enabled 2.0 rules can therefore begin running on matching pages after the update without starting a recording session.

The Playground can enable an example after one approval and disable its rule directly. The SDK adds `enableRule`, `disableRule` and `deleteRule`; rule replacement is clearly labeled as an update, and credential notices are translated into all six supported languages.

## Upgrade an existing website integration

Update the dependency to `wireflip@2.1.0` when the release is available. Connect before the user's click, call changes from the click handler, check extension capabilities before using newer APIs, and show returned errors in the website. See [SDK examples](../packages/npm/readme.md).

Published `wireflip@0.2.0` stops waiting after five seconds for some operations. The new extension immediately rejects an old-client request when it needs approval, with upgrade guidance. It does not leave an approval window that can execute after the website reports a timeout. Read-only calls still work; manually trusted sites may continue ordinary operations, but credential access still needs the updated SDK. Existing unowned rules still require management in Wireflip.

The original `cors-unlocker` hosted bridge and extension IDs remain supported. Keep the original `cors.forth.ink` bridge address; changing its hostname is not an SDK upgrade.

## Browser limits

Chrome prepares matching tabs asynchronously. Requests sent before rule readiness may pass through, and Chrome may display its native debugging indicator. Firefox response-body replacement still contacts the upstream server and preserves its status. Saved rules persist across page refreshes and revisits until changed in Wireflip.

## Coordinated availability

Use one release version, release window and announcement for Chrome, Firefox and npm. Submit both store updates and coordinate npm publication; store review and update propagation can complete at different times. Announce general availability only after all three channels are verified. During rollout, capability-check newer APIs and do not assume an installed extension has updated merely because the npm package is available.

Store submissions, actual existing-profile update checks, signed-package verification and npm publication remain separate release actions. See [the release checklist](../docs/release-2.1.md). Do not mark these channels as published or replace the recorded 2.0.0 fingerprints merely because this PR is merged.
