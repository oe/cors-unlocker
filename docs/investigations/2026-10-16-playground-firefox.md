# Firefox Playground 验收缺口

用户报告：默认 Mock 示例直接请求得到原站内容；创建规则后默认关闭，手动启用后仍得到原站内容。

## 原因

SDK 连接成功只证明网页可以与扩展通信。网站创建的规则必须保持默认禁用并限定来源，这是已有的授权边界。Mock 还依赖 Playground 所在标签页的会话；工作区标签页或另一个标签页启动的会话不替代它。

旧 Playground 允许在没有规则或没有会话时发送请求，把普通 HTTP 响应标成绿色成功，也没有校验返回体。此前官网验收用网络 fixture 检查请求 UI，扩展和 SDK 分别测试，没有覆盖商店插件和 Playground 的完整使用流程。这是产品交互和验收缺口，不能要求用户自行推断。

## 修复

- 明确添加并启用规则、返回 Playground 标签页启动会话、测试这三个步骤
- 无扩展、未添加配方、所需会话未启动时禁用测试；发送前重新读取会话状态
- 可见页面定期刷新状态，停止会话后重新锁定测试
- Mock 的成功依据是实际响应体匹配，原站内容或其他响应明确显示未匹配
- 请求使用 cache: no-store，避免先前原站响应的 HTTP 缓存干扰
- 已添加配方的按钮改为重新打开工作区，当前标签页刷新后保留草稿记录，避免重复创建

SDK 不暴露已启用规则列表，所以网页不能提前确认用户是否开启规则、组是否暂停、是否存在其他覆盖规则。页面明确要求启用，测试用实际响应验证，不虚构规则就绪状态。

## 验收

新增 `Playground against public Firefox` 工作流，安装未改动的 AMO 2.0.0 签名包（文件 5122149，SHA-256 37828cb7a9695964b79e4b583ddb31d7c61c15bb8701f82668bb8cd633831301），通过构建后的网页、工作区开关和 Popup 启停执行真实请求。

两条链路分别覆盖默认公网 JSONPlaceholder 配方，以及返回 418 且允许缓存的真实本地 HTTP 端点。后者先验证“规则开启、会话关闭”仍得到服务器内容，再启动会话验证 Mock 和原始 418 状态，关闭规则验证未匹配，停止会话验证按钮禁用。无 fetch 或扩展 API mock。

[首轮两条链路通过，Firefox 157.0.1](https://github.com/oe/cors-unlocker/actions/runs/38831433914)。最终提交以 PR 的必需检查记录为准；生产部署之后还需按发布 checklist 在实际站点人工走查。
